# Security audit

**Method:** non-invasive static review only. Severity describes potential impact if the code is deployed in a reachable configuration; exploitability was not tested. No credentials or user data are reproduced.

| ID / severity | Finding and impact | Evidence | Recommended remediation |
|---|---|---|---|
| S-01 Critical | Core object authorization is absent. There are no file/warehouse routes or membership model. If file handlers are added without enforcing warehouse scope on each object operation, cross-tenant disclosure/deletion becomes likely. | `packages/database/prisma/schema.prisma` has no Warehouse/StoredFile/membership models; route registry has no file routes. | Add warehouse membership and resource-level policy checks; derive warehouse from authorized object metadata, never trust caller-supplied IDs alone. Add cross-warehouse deny tests before release. |
| S-02 High | Session middleware logs the raw `Cookie` request header at info level, likely exposing live session credentials to log systems. | `apps/api/src/middleware/auth.ts`, `requireAuth` log object includes `cookieHeader: request.headers.cookie`. | Remove cookie/token values from logs; log request ID, auth outcome, and non-sensitive identity only under access controls. Review retention and rotate/revoke sessions if logs are exposed. |
| S-03 High | Host/proxy trust is broad. Fastify uses `trustProxy: true`; Better Auth enables trusted proxies. Incorrect direct exposure can let client-supplied forwarding headers influence IP/scheme/cookie/rate-limit decisions. | `apps/api/src/app.ts`; `packages/auth/src/server/auth.ts`. | Set explicit trusted proxy ranges/topology; terminate TLS at known proxy; test spoofed forwarding headers at edge. |
| S-04 High | Account creation/password paths have divergent hashing behavior. Admin routes store scrypt hashes while Better Auth normally owns credential hashing; compatibility is unverified. Recovery/reset behavior may fail or create inconsistent credentials. | Manual `hashPassword` in `apps/api/src/routes/users/index.ts`; Better Auth credential account integration in `packages/auth/src/server/auth.ts`. | Use Better Auth supported account APIs or one documented hasher; test create/login/reset/upgrade flows; avoid hand-editing adapter-managed credential rows. |
| S-05 High | Privilege assignment may be over-restricted in one path and privilege-escalating in another: role assignment endpoint accepts any role ID when caller has `ASSIGN_ANY`; user update silently only applies `roleIds` for superadmin though UPDATE permission allows the endpoint. General role permissions may let a delegated admin assign a SuperAdmin/system role. | `apps/api/src/routes/roles/index.ts` POST `/:id/users`; `apps/api/src/routes/users/index.ts` PUT `/:id` roleIds branch. | Define role hierarchy and assignable-role policy; block system/SuperAdmin grant except explicit protected bootstrap path; make assignment atomic and explicit; test horizontal/vertical escalation. |
| S-06 High | Rate limiting is opt-in and likely process-local; broad sensitive routes do not declare limits. It will not coordinate across replicas. | `apps/api/src/app.ts` registers `{ global:false }`; only custom check-user is visibly configured; Better Auth has a separate 100/min config. | Apply route-specific limits to login/OTP/recovery/API-key and expensive operations; shared Redis-backed limiter in multi-instance deployments; consider IP and account/key dimensions. |
| S-07 High | Public recovery and cooldown endpoints accept raw phone strings and reveal cooldown state for any supplied number. Validation/rate controls are minimal; enumeration and resource abuse are possible. | `apps/api/src/routes/recovery.ts`; cooldown is unauthenticated GET; phone schema is plain string. | Normalize E.164; return uniform responses; apply shared limits; bind reset actions to verified proof; avoid unauthenticated sensitive state disclosure; use DB atomic counters/unique windows. |
| S-08 High | Health endpoint reveals operational configuration and detailed DB exception text, including a partially masked database URL with host/database/query and secret fragments/lengths. | `apps/api/src/routes/health.ts`: `maskDatabaseUrl`, `maskSecret`, dbStatus error message, config response. | Public health should return minimal liveness/readiness only. Move diagnostics behind authenticated/internal-only channel; never return URLs, secret fragments, or raw driver errors. |
| S-09 High | Compose startup automatically applies migrations and seeds, creating deployment-time schema mutation and possible bootstrap-account risk. | `compose.yml` API `command` calls migrate deploy and seed before server. | Run reviewed migrations as a release job; ensure seed is idempotent, never reset credentials unexpectedly; separate bootstrap from normal startup. |
| S-10 Medium | `Dockyard POST` is incomplete and has no response. Authorization is present but operation is unusable and may hang until framework timeout. | `apps/api/src/routes/admin/dockyard.ts` POST handler ends after validation. | Complete with schema-aligned creation, transaction/error response/tests, or remove route pending product decision. |
| S-11 Medium | Session/auth cookie policy and cross-subdomain domain construction need deployment verification; cookie domain uses last two hostname labels, which is incorrect for many public suffixes and may broaden cookie scope. Secure behavior is not explicit here. | `packages/auth/src/server/auth.ts` derives `cookieDomain`; cookie options rely on library defaults. | Configure explicit canonical domain and secure/httpOnly/sameSite policy; do not derive registrable domain by taking last two labels; validate HTTPS production settings. |
| S-12 Medium | `check-user` reports whether a phone number exists, enabling account enumeration; it has route limit but limiter store/distributed behavior is unknown. | `apps/api/src/routes/auth/custom.ts`. | Return non-enumerating responses where feasible; shared throttle, normalized input, monitoring. |
| S-13 Medium | Zod errors and caught exceptions are sometimes returned directly to clients, while generic catch blocks can flatten error classes into 400. This risks internal detail disclosure and inconsistent semantics. | `apps/api/src/routes/roles/index.ts`; `apps/api/src/routes/auth/custom.ts`. | Centralize error mapping; expose safe validation errors, log sanitized internal details with correlation IDs. |
| S-14 Medium | File-specific threats cannot be assessed as implemented because file operations do not exist. Required controls remain absent: filename/path safety, MIME/content sniffing, streaming quotas, malware scanning, checksums, storage encryption/key management, deletion reconciliation, and signed URL replay/revocation policy. | No file/storage source found; multipart config alone in `apps/api/src/app.ts`. | Make controls explicit acceptance criteria in file phase; use opaque generated object keys, content inspection, bounded streaming, at-rest encryption policy, malware pipeline where risk requires, immutable audit events and retention rules. |
| S-15 Medium | Credential/account role mutations use multiple non-transactional DB writes; partial failures can leave user without credential or inconsistent roles. | `apps/api/src/routes/users/index.ts` user create, role replacement and password changes. | Use Prisma transactions and explicit consistency rules; test injected failures and concurrent updates. |
| S-16 Low/Medium | CORS uses configured origin list with credentials; correctness depends on deploy env and proxy/cookie topology. No CSRF protection is visible for cookie-authenticated state-changing routes. | `apps/api/src/app.ts`; credentialed cookie auth. | Restrict exact origins; add CSRF strategy (SameSite plus origin checks/token as appropriate) and test cross-origin state-changing requests. |

## Threat areas with no implementation to assess

No signed URL function exists, so signature strength, expiry enforcement, path/resource binding, timing-safe comparison, leakage in referrers/logs, and replay semantics are unverified and currently missing. No API-key material exists to assess storage/rotation/revocation; implement hashed secrets, prefix-based lookup, scopes, expiry, last-used throttling, and one-time display. No storage encryption/key-management implementation exists. Do not describe these as existing safeguards.

## Security release gates

1. Remove sensitive auth/config details from logs and health responses.
2. Explicitly pin trusted proxy and cookie domain policy.
3. Prove role assignment cannot grant system privileges unintentionally.
4. Enforce warehouse isolation on every list/read/write/delete/sign operation.
5. Add distributed abuse controls for auth, recovery, API keys, and file ingestion.
6. Cover the above with automated negative tests before external exposure.
